## 1. 分层状态机与行为树

### 宏状态（AgentMacroStateId.cs:7-17）

每个状态的含义是根据工厂代码和转移规则归纳出来的。

| 值 | 含义 |
|---|---|
| None=0 | 只给两个容器状态用："AgentRoot" 和 "Raid"（AgentBrainStateFactory.cs:19-35）。两者都没有行为树，也没有转移。 |
| Explore=1 | 默认的空闲叶子状态，是 Raid 的初始子状态（AgentBrainStateMachineFactory.cs:51 `AddChild(exploreState, true)`）。它的树只是一个占位节点，不执行任何指令。 |
| Combat=2 | 执行 Engage + Enemy 指令。 |
| SearchResource=3 | 执行 Search + Resource 指令：走到资源群里的箱子或掉落物，然后等玩家开、关背包。 |
| InteractLoot=4 | 和搜索共用同一棵树（AgentBrainStateFactory.cs:96-102）。进入条件是 HasInteractableTarget=true，但全仓库没有任何代码把它写成 true，只有写 false 的地方（AgentDirectiveLifecycleController.cs:152、AgentTargetDiscoveryController.cs:327、AgentTargetDecisionController.cs:333）。所以这个状态目前实际进不去。 |
| Extraction=5 | 执行 Extract 指令：走到撤离点，再把"人在点内"桥接给 RaidFlowController。 |
| InvestigateEnemySource=6 | 执行 MoveTo + EnemySource 指令（玩家点击敌人来源群时生成），只靠近侦查，不接战（AgentBrainStateFactory.cs:137）。 |
| Navigate=7 | 执行 MoveTo + Location 指令，也就是路线锚点移动，由 AgentClusterStepExecutor.cs:151-161 生成。 |

- 层级结构是 AgentRoot → Raid → 7 个叶子（AgentBrainStateMachineFactory.cs:49-57）。`Build()` 的注释写"六个宏状态"（:29-30），实际建了 7 个叶子，多出来的是 Navigate。
- 转移只挂在叶子上，按优先级取最高的一条：
  - ToNavigate 优先级 120，另外 6 个叶子都有（:60-62）。
  - 玩家手动搜索抢回资源搜索，110（:95-99、:170-174、:195-199）。
  - 进入 Combat 100，InvestigateEnemySource 95，SearchResource 90，Extraction 80，回到 Explore 70 或 80。

### 行为树怎么挂到状态上

- `AgentBrainState(macroStateId, name, boundBehaviorTree)` 把树传给基类 `StateMachineState`（AgentBrainState.cs:19-26）。`OnEnter` 把 CurrentMacroStateId/Name 写进黑板（:33-46）。
- `StateMachineState.Enter` 为这棵树新建一个 `BehaviorTreeRunner`（StateMachineState.cs:92-97）。`Update` 每帧 Tick 它（:108-111）。`Exit` 时如果树还在跑，就以 ExternalAbort 中断，然后丢弃 runner（:123-132）。
- 每个 Agent 的 AgentBrainController 构造时各自建一套状态机和树实例（AgentBrainController.cs:110-133）。所以节点字段是每个 Agent 私有的；同一状态多次进入时复用同一组节点实例，靠 OnEnter/OnAbort 重置。

各状态绑定的树（AgentBrainStateFactory.cs）：

| 状态 | 树结构 |

| Navigate | `MoveToTarget(MoveTo, Location, MoveStoppingDistance, 2f, finishDirectiveOnArrival:true)`（:49-53） |
| Combat | `EngageEnemyActionNode`（:130-133） |
| InvestigateEnemySource | `MoveToTarget(MoveTo, EnemySource, MoveStoppingDistance, 2f)`（:135-146） |
| SearchResource / InteractLoot | `Sequence(MoveToTarget(Search, Resource, InteractionDistance, 1.5f), SearchResourceActionNode)`（:148-162） |
| Extraction | `Sequence(MoveToTarget(Extract, Extraction, …, 1.5f), ExtractActionNode)`（:164-178） |

### 行为树库

- 是项目自研的，命名空间 `Core.BehaviorTree.*` / `Core.StateMachine.*`。Packages/manifest.json 里没有第三方行为树或状态机包。
- 节点基类 `BehaviorNode` 提供 Enter/Execute/Exit/Abort，`Execute` 首次调用时自动 Enter（BehaviorNode.cs:24-72）。节点结果只有 Success、Failure、Running 三种。
- 库里有：
  - 组合节点：SequenceNode（SequenceNode.cs:34-61）、SelectorNode（SelectorNode.cs:34-63）。
  - 叶子：ActionNode、ConditionNode、SubtreeNode。
  - 装饰器：BlackboardCondition、Cooldown、Observer、Repeater、Timeout。
- Agent 的树实际只用到 SequenceNode 加自定义的 ActionNode。SequenceNode 只出现在 AgentBrainStateFactory.cs:153 和 :169，Selector、装饰器和 Condition 在 Gameplay 代码里都没用到。
- Runner 在根节点返回非 Running 后执行 Exit，下一次 Tick 会重新进入，也就是说树跑完会自动重启（BehaviorTreeRunner.cs:47-62）。

### AI/Actions 里的节点（各一句）

- **AgentActionNodeBase**：公共基类。从 UserContext 取 IAgentReadOnly；按指令类型读取黑板 `PendingDirectiveRequest`，类型不符就不处理；负责目标位置解析和移动（经 `MoveDirective`）；`ClearPendingDirective` / `FailPendingDirective` 最终都调用 `FinishDirective`（:38-67、:304-327）。
- **MaintainMacroStateActionNode**：只写 CurrentMacroStateId/Name，永远返回 Running（:26-41）。
- **MoveToTargetActionNode**：读取指定类型和目标种类的指令并移动过去（资源取最近的未处理成员，撤离取最近的撤离点），到达返回 Success，可选到达即结束指令（:44-113）。
- **EngageEnemyActionNode**：能开火就停步、放技能或射击；不能开火就有界追击。敌人死亡或目标丢失算完成；超时、不可达或攻击不可用算失败（:49-194）。
- **SearchResourceActionNode**：在资源群里逐个处理最近的未处理成员。空箱直接完成；有物品就等玩家对这个 Agent 开、关背包；背包容量不足时写 InventoryRequiresExtraction（:112-157、:277-313、:415-465）。
- **ExtractActionNode**：到达撤离点后每帧调用 `SetAgentInsideExtractionPoint(true)`，离开或被中断时写 false，节点本身永远 Running（:27-68、:119-156）。

## 2. 边界：谁决定宏状态转移

**结论**：转移由状态机的转移规则决定，但这些规则几乎只读两样东西：生命周期活动槽里那条指令在黑板上的镜像，加上少量事实。行为树只执行和结束当前指令，从不创建或替换指令。树的 Success/Failure 也不参与转移判断。

### 机制

1. **指令放在哪**：`AgentDirectiveLifecycleController` 有一个活动槽 `_active` 和一个挂起槽 `_suspendedDirective`（:17-18）。
   - `Activate` 通过 `AgentInterventionController.SubmitDirective` 把请求写入黑板 `PendingDirectiveRequest`（AgentDirectiveLifecycleController.cs:125-131；AgentInterventionController.cs:29-40）。
   - `SetTaskFacts` 同时写 ShouldExtract、HasResourceTarget、HasInteractableTarget=false、HasEnemySourceTarget、HasVisibleEnemy（:146-155）。
   - `Tick` 会在目标失效或完成时自动 Finish 当前指令（:112-120）。
2. **每帧顺序**（AgentPawnRoot.cs:216-227）：身体事实 → `_directiveLifecycle.Tick()` → `_routeController?.Tick()` → `_brainController.Tick()`。
   - 状态机 `Update` 先评估转移，再 Tick 树（HierarchicalStateMachine.cs:70-78）。
   - 评估时从叶子向上找第一个有可触发转移的状态，取其中优先级最高的（:120-158）。
3. **转移条件就是黑板谓词**（AgentBrainTransitionRules.cs）：
   ```csharp
   CanEnterNavigate => !dead && PendingDirectiveRequest is MoveTo && Kind == Location   // :16-19
   CanEnterCombat  => !HasManualResourceDirective && !isDead && HasPendingEnemyEngageDirective(context) // :30-38
   ```
   - Extraction 需要 ShouldExtract 为真，并且挂着的是 Extract 指令（:140-147）。
   - 资源工作被战斗打断，需要满足其一：最近 1.25 s 内受过战斗伤害，并且挂着受击反击指令；或者资源目标已清空，并且挂着 Engage/Enemy 指令（:14、:82-99）。
   - 注释和代码不一致：CanEnterCombat、CanExtractionBeInterruptedByCombat、CanLeaveCombatToExplore 的注释写"有/没有可见敌人"，但局部变量 hasVisibleEnemy 没被用到，实际只看指令（:35-37、:224-227、:157-162）。
4. **状态机不看树的结果**：Gameplay 代码里没有任何地方读 `BehaviorTreeRunner.LastResult`，也没有调用 `ForceTransition`。树结束后会自动重启，直到转移规则把状态切走。
5. **树对指令只做"结束"**：
   - `FinishDirective(commandId[, failure])`（AgentActionNodeBase.cs:304-316）；Navigate 到达即结束（MoveToTargetActionNode.cs:110-111）；导航失败时由 AgentPawnRoot.cs:524-531 代为以 NoProgress/Unreachable 结束。
   - AI/ 目录里搜不到任何 Submit / TrySubmit 调用。
   - 树写的事实只有：HasVisibleEnemy=false（EngageEnemyActionNode.cs:198）、HasResourceTarget/HasInteractableTarget=false（SearchResourceActionNode.cs:361-362）、InventoryRequiresExtraction=true（:455）、宏状态 Id/Name。
   - 树会在指令范围内做执行层选择，但不改指令本身：群内最近的存活敌人（EngageEnemyActionNode.cs:203-223）、群内最近的未处理资源（SearchResourceActionNode.cs:117-121）、最近的撤离点（ExtractActionNode.cs:83-95）、射击接近点。
6. **结束之后的恢复由生命周期决定**（Finish，AgentDirectiveLifecycleController.cs:69-91），不由树决定。MoveToTargetActionNode 释放指令后会返回 Running，注释写的是"等待宏状态切换"（:86-91）。
7. **指令来源都在树外**：
   - 玩家：AgentTargetCommandDispatcher。
   - 自主：AgentTargetDiscoveryController / AgentTargetDecisionController。
   - 受击：AgentPawnRoot.RecordCombatDamageInterrupt。
   - 路线：AgentClusterStepExecutor 调用 `SubmitRouteStep`。

`MaintainMacroStateActionNode` 只是 Explore 的占位，目的是"让每个宏状态都真正绑定一棵行为树"（:28-29），本身不驱动任何转移。

## 3. 挂起与恢复：进度存在哪里

### 挂起（AgentDirectiveLifecycleController.SubmitCore）

```csharp
if (damageInterrupt && _active.HasValue && !_suspendedDirective.HasValue &&
    (IsManualDirective(_active.Value) || _active.Value.DirectiveType == AgentDirectiveType.Extract || _active.Value.RouteContext.IsValid))
{ _suspendedDirective = _active; Publish(_active.Value, AgentDirectiveStage.Suspended); }   // :58-63
else if (_active.HasValue) Publish(_active.Value, AgentDirectiveStage.Cancelled, AgentDirectiveFailure.Superseded); // :64
```

- 会被挂起的：玩家指令、撤离指令、任何路线步骤（包括自主路线的步骤）。
- 普通自主指令直接取消，不挂起。
- 挂起槽只有一个。

### 恢复（Finish）

```csharp
bool resume = AgentManualDirectiveLock.IsCombatDamageDirective(completed);           // :73
... if (targetFailure != None && IsTargetCompletion(suspended, targetFailure)) { Publish(suspended, Completed); return true; } // :80-85
if (validation == None) { Activate(suspended); Publish(suspended, AgentDirectiveStage.Resumed); }  // :86-87
else Publish(suspended, Failed, validation);                                                         // :88
```

- 恢复的是同一个请求值：CommandId、RouteContext、ResourceSearch 引用都和挂起前一样。
- 对应测试：ManualDirectiveResumeTests.cs:65-72、AgentRouteLifecycleTests.cs:22-44。

### 进度分层存放

**(a) 路线层：计划和游标都保留，恢复时不重新规划**
- `AgentRouteController._state` 里有 Request、Version、Plan、Cursor、EntryFromNodeId、ReplanCount、SkipResources（AgentRouteState.cs:6-15）。`_step`（AgentClusterStepExecutor）记录当前阶段、`_anchorVisited`、`_failedAttempts`、`_commandId`。这些都不受挂起影响。
- 代码注释也写明了这一点：AgentRouteState 是"保存根序列，不保存受击挂起指令"（:3）；AgentRoutePlan 是"冻结结果…不持有执行游标"（:6）。
- 反击期间路线层被显式冻结：
  - 步骤执行器直接返回，并顺延等待计时：`if (IsRetaliating) { _waitStarted = now; _retryAt = now; return; }`（AgentClusterStepExecutor.cs:67）。
  - 步骤完成时 `if (IsRetaliating) return;`（AgentRouteController.cs:119）。
  - `BeginReplan` 直接返回（:195）；正在进行的重规划等待反击结束（:140）。
  - 步骤的 `OnResult` 只关心 Completed/Failed/Cancelled（AgentClusterStepExecutor.cs:178-183），所以 Suspended/Resumed 不会让步骤终止。恢复后 CommandId 没变，`Owns()` 仍然成立（:176）。
- 测试 AgentRouteExecutionTests.cs:282-296 断言反击后 StepIndex 和 RouteVersion 都不变。
- 只有恢复之后步骤再以 StaleContext、Unreachable、NavigationNotReady 或 NoProgress 失败时才会重规划；重规划沿用同一个 Request，最多 2 次（AgentRouteController.cs:123-125、:193-203）。

**(b) 资源层：哪些箱子已处理**
- `ResourceSearchPass` 只存一个起始修订号 `_startedAtRevision = AgentSearchedResourceRegistry.Revision`（ResourceSearchPass.cs:12-14）。注释："起始版本随指令挂起/恢复及同根重规划保留；新的玩家命令才会重新允许处理余物"（:7-8）。
- 处理记录存在全局静态的 `AgentSearchedResourceRegistry` 里（InstanceID → 修订号），所有 Agent 共享（AgentSearchedResourceRegistry.cs:12、:19-25、:39-41）。
- Pass 在这些地方创建或传递：
  - 直接玩家指令：AgentTargetCommandDispatcher.cs:63-64。
  - 玩家路线：AgentRouteRequest.cs:27、AgentClusterStepExecutor.cs:53。
  - 解析器把它塞回 Search 指令：MapGraphRouteTargetResolver.cs:111。
- 恢复后 `HasPendingResources(search)` 和 `IsMemberAvailableForSearch` 会跳过本轮已处理的成员（ResourceClusterAuthoring.cs:69-74、:446-453），所以从剩下的箱子继续。测试见 ResourceSearchRevisitTests.cs:195-240。

**(c) 生命周期层**：挂起槽本身（AgentDirectiveLifecycleController.cs:18）。

**(d) AgentManualDirectiveLock 不存进度**，只是一组静态判定。反击期间它让自主发现和决策直接跳过扫描（AgentTargetDiscoveryController.cs:153-158、:200-203；AgentTargetDecisionController.cs:104-117）。

### 不保留、会从头开始的部分

- **树节点的内部状态**：状态退出时 runner 被中断并丢弃（StateMachineState.cs:123-132）。SearchResourceActionNode 在 OnAbort/OnEnter 里调用 `ResetSearchState`，当前箱子和正在等待的背包会话都会清空（:39-42、:256-260、:509-517）。EngageEnemyActionNode 在 OnEnter 里重置计时（:41-47）。
- **导航电机**：`Activate` 时调用 `_motor.Reset(commandId)`（AgentDirectiveLifecycleController.cs:130），卡死检测和进度都清零（AgentNavigationMotor.cs:35-38）。
- **撤离倒计时**：ExtractActionNode 中断时写 false（:58-68），RaidFlowController 删除该 Agent 的进度条目（RaidFlowController.cs:224-231），恢复后从 0 开始计时。

**小结**：粗粒度的进度（走到第几个群、哪些箱子处理过）会保留；细粒度的执行状态会重来，Agent 会重新寻路到最近的未处理成员。

## 4. 仲裁规则

### AgentRouteController.Submit（AgentRouteController.cs:69-96）

- **两种来源都适用的拒绝**：

  | 情况 | 拒绝原因 | 行号 |
  |---|---|---|
  | Agent 已销毁或死亡 | AgentUnavailable | :72 |
  | 没有地图 | MapUnavailable | :73-74 |
  | RequestId 为空或 Source 非法 | InvalidRequest | :75-76 |
  | 解析不到目标节点 | MissingTarget | :77-85 |
  | 节点不可通行 | TargetUnavailable | :86 |

- **去重**：待规划的请求目标相同时返回 Planning；活动路线目标相同且没有待规划请求时返回 Accepted（:87-90）。"目标相同"指 TargetNodeId 和 Source 都相同（:226）。
- **只有自主请求会被拒**：
  ```csharp
  if (request.Source == AgentRouteSource.Autonomous && (_state?.IsActive == true || _pending != null || IsRetaliating))
      return Publish(request, 0, AgentRouteStage.Rejected, AgentRouteFailure.Superseded);   // :91-92
  ```
  只要有任何活动路线（不管是玩家的还是自主的）、任何待规划请求，或者正在受击反击，自主请求就以 Superseded 被拒。
- **玩家请求**：
  - 通过上面的通用检查后，永远不会因 Superseded 被拒。它会把旧的待规划请求拒掉，新建规划任务并返回 Planning（:93-95）。
  - Submit 返回的只是 Planning。真正的 Accepted 要等首个步骤 `TryBegin` 成功后才发布，同时把旧的活动根发布为 Cancelled/Superseded（:166-176）。
  - 规划参数：每 Tick `Advance(4)`（:150）；墙钟期限 8 s（:130）；环境变化最多重启 3 次（:159）。新的玩家规划在反击中也能推进，只有重规划需要等反击结束（:140）。
- **自主候选的事前过滤**：`CanSelectAutonomousTarget` 结合 `AgentRouteFailureMemory`，只记录自主请求的失败（AgentRouteController.cs:48-54；AgentRouteFailureMemory.cs:40-66）：
  - Unreachable、Disconnected、NoReachableEntry、NavigationNotReady：屏蔽时间不限，直到环境、成本或目标修订变化，或 Agent 移动超过 2 m（:25-28）。
  - NoProgress、SpawnFailed、NoExecutableMember、StaleContext、TargetUnavailable：屏蔽 3 s。

### 生命周期层（SubmitCore :35-67）

- 先做校验，失败就拒绝。受击打断时放行 NavigationNotReady（:39-41）。
- 自主指令（不是受击打断，也不是路线替换）遇到活动槽里是玩家指令、受击反击或任何路线步骤时，以 Superseded 被拒（:52-54）。
- 非玩家指令且和当前活动指令目标相同：直接返回 Accepted，不重置（:55-56）。
- 玩家指令或路线替换：先丢弃挂起槽（:57），再取消当前活动指令，包括正在进行的反击（:64）。
- 入口分流（AgentPawnRoot.cs:475-480）：如果装了路线、请求没有 RouteContext、又不是受击指令，就走 AgentRouteDirectiveAdapter。其中 `IsManualDirective` 为真的算 Player，其余算 Autonomous（AgentRouteDirectiveAdapter.cs:57-62）。
- "玩家指令"的判定（AgentManualDirectiveLock.cs:67-75）：有 RouteContext 时看 `IsPlayerRoute`；否则要求 Priority ≥ 1000 且 CommandId 以 "ManualTargetClick" 开头。

### 受击反击的优先级（AgentManualDirectiveLock.cs:15-17、:90-99）

- **何时生成**（AgentPawnRoot.cs:333-343、:534-562）：
  - 伤害来源必须能解析成 EnemyHealthController，造成了实际伤害，且 Agent 没死。
  - 先写 LastCombatDamageTime。

- **反击能做的**：挂起玩家、撤离和路线步骤；取消普通自主指令；同时屏蔽所有自主提交（生命周期层、路线层、发现与决策层都会拦）。

## 5. 感知与接战

**TargetVisibilityQuery**（TargetVisibilityQuery.cs:7-43）按以下顺序判定：
1. 目标为空或未激活 → Invalid。
2. 瞄准点取目标第一个启用的非 Trigger 碰撞体的当前几何中心，没有就取 position+up（CombatAimPointResolver.cs:7-14）。
3. 瞄准点到起点的三维距离超过 range → OutOfRange。
4. angle < 360 时，平面夹角超过半角 → OutsideView。
5. 从起点到瞄准点做 RaycastAll（忽略 Trigger）。命中任何既不属于观察者最近父碰撞体层级、也不属于目标层级的碰撞体 → Occluded。另用 0.02 m 的 OverlapSphere 捕获包住射线起点的碰撞体，也算 Occluded。
6. 以上都不成立 → Visible。

Agent 这边的调用全部用默认 angle=360，即没有视锥。实际开火还要再过 `AgentCombatShooter.CanShootAt`：枪口可见，并且按子弹半径做的 ProjectileSweepQuery 球扫没有阻挡（AgentCombatShooter.cs:26-42、:164-168）。

**AgentTargetCandidateCollector.CollectVisibleEnemies**（:21-47）：
- 只遍历启用且未完成的 ActiveEnemyClusterAuthoring。每次调用都清空 `_seen`，按敌人 InstanceID 去重。
- 去重发生在可见性检查之前（`!_seen.Add(id) || Check(...) != Visible`，:34）：一个敌人只被第一个包含它的群认领，也只检查一次。
- 可见性用发现半径（TargetDiscoveryRange，默认 30）。
- 所有可见敌人都会入列，但只有满足 `CanExecute` 的会被选中：路线允许选该群，并且（已在攻击距离内，或者能找到射击位置），并且不在失败记忆的延期期内（:39-41）。
- 结果先按距离平方、再按 InstanceID 排序（:46）。调用方只选 CanExecute 的候选（AgentTargetDiscoveryController.cs:224-225；AgentTargetDecisionController.cs:196）。
- 失败记忆：遇到 LostSight、Unreachable、NoProgress、NavigationNotReady、AttackUnavailable 失败后延期 3 s；Agent 或目的地移动超过 0.5 m 就解除；手动指令不查这个缓存（AgentTargetFailureMemory.cs:9-13、:41-76）。
- 资源、敌人来源和撤离点候选另外要求完整路径可达，即导航结果为 Arrived 或 Moving（:118-123）。

**AgentCombatApproachQuery.TryResolve**（:18-57）：只返回"有完整路径能到、并且站在那里真能开火"的位置。不完整路径在 AgentNavigationQuery.cs:31-32 里直接算 Unreachable。按顺序尝试：
1. 敌人的地表点（AgentCombatNavigationTarget.cs:9-26）能直达且能开火，就用它（:24-28）。
2. 如果直达路径是 Partial，就用这条部分路径的最后一个拐点做候选（:29-35）。
3. 以敌人 XZ 坐标加 Agent 地面高度为中心、朝 Agent 方向做环扫（:36-54）：
   - ring0：中心 1 个点。
   - ring1：8 个方向，半径 0.5 × attackRange。
   - ring2：8 个方向，半径 0.85 × attackRange。
   - 每个点做 `NavMesh.SamplePosition`（半径 max(0.5, 2 × nav.radius)，同 agentType 和 areaMask），并要求到该点的完整路径终点偏差不超过 0.05 m（:70-79）。

"能开火"的判定（:81-96）：把 Agent 当前的 transform 和身体瞄准点平移到候选点（保留 baseOffset 和缩放），要求身体瞄准点 Visible，并且转向敌人后 `shooter.CanShootFrom` 成立（枪口可见，弹道球扫无阻）。

**看不见时的有界追击**（EngageEnemyActionNode.cs:94-149）：
- 不能开火时，取两个信号：
  - observed：黑板 HasVisibleEnemy，由生命周期每帧按发现半径重算（AgentDirectiveLifecycleController.cs:121-122、:156-162）。
  - obstructed：最近一次射击检查结果是 Occluded。
- "看得见且没被挡"时计时清零，否则开始计时；计时达到 CombatLostSightTimeout 就以 LostSight 失败（:96-107）。

- 连续受击不会重置追击：生命周期直接返回现有的反击（:44-48），节点只在 CommandId 变化时才重置计时（:56-60）。
- 另外，路线步骤在前往敌群锚点的途中，如果进入攻击距离且敌人可见，会每 0.25 s 探测一次并提前开打（AgentClusterStepExecutor.cs:128-149）。

### 1. 结构剖面
**结论：** 做法是"导出模型里预先拆好的网格 + 逐件抖动淡出 + 同一网格的菲涅尔轮廓幽灵"。没有剖切平面，没有运行时切网格，没有模板缓冲，也没有着色器按平面裁切。

- **数据来源**
  - PartsCatalog.json 里每个网格都有一个 `cut` 布尔值（Catalog:35）。
  - 外壳在导出时已拆成 `*Fixed` + `*Window` 两件，Window 那件 `cut=true`。例：R01 JacketFixed/JacketWindow，R02 VoluteFixed/VoluteWindow，R03 ManifoldFixed/ManifoldWindow。
  - 每件样品中可剖去的网格数：R01 2/20，R02 8/21，R03 3/19，R04 2/19，R05 6/23。
  - 载入时把 `cut` 写进每个 Pose（Stage:120-128）。
- **隐藏逻辑**（SMotion:102-106）
  - `float visible = Mode == "cutaway" && p.cut ? 0 : 1;`
  - 用 Ease 在 0.42 s 内过渡，visibility ≤ .001 时关掉 renderer。
- **PBR 里的 clip 只是溶解，不是剖切面**（PBR:56-58）
  - `clip(_Visibility-.001-dither*.998);` 是屏幕门抖动淡出，作用是保住不透明深度。
  - `_Visibility` 通过 MaterialPropertyBlock 写入（Analysis:196, 202）。
- **幽灵轮廓**
  - Analysis:42-54：每个 cut 件生成一个子物体 `Section_Silhouette`。它共享同一个 sharedMesh，放在 layer 31，不投影。材质是 AnalysisOverlay，`_EdgeOnly=1`，青色 (.36,.8,.9)。
  - Analysis:203-207：visibility < .98 时启用，`_Opacity = (1 - p.visibility) * .32f`。
  - Overlay 着色器（HEAD 版第 3-28 行）：Transparent+10、Alpha 混合、ZWrite Off、Cull Off，alpha = opacity × pow(1-|N·V|,5)。
  - 幽灵材质没有覆盖 `_ZTest`，用默认值 4（LessEqual）；教学路径材质才改成 Always（Analysis:41）。
  - 幽灵是 Pose 的子物体，所以会跟着分解位移一起走。
- **相关联动**
  - 点热点会按它的 `view` 字段自动切换模式（Stage:162）。
  - R01/R02 的原理演示强制进入剖面（Analysis:140）。

### 2. 分解观察
- **位移向量是数据，不在运行时计算**
  - 来自 PartsCatalog.json 每个网格的 `explode` float[3]，坐标是 Blender Z 轴朝上。
  - 由 `Convert` 转成 (x,z,y)（Catalog:25），乘上模型归一化比例，再变换到父节点局部空间（Stage:122, 127）。
  - 代码注释写的是 "exported assembly offset"（Stage:123-124），文档写"机械分组使用现有导出位移"（Docs:72）。
  - 生成这些数据的导出脚本和五个 Blender 母版：**not found**。仓库里只有 FBX，`tools/art/build_wenchang_landing.py` 是着陆场火箭用的，和样件无关。
- **"组件组"没有显式 ID**
  - explode 向量完全相同的网格，位移和时序就完全一样，这就是"同组紧固件一起动"的实现。
  - 例：R02_Fasteners 与 VoluteFixed / FeedInterfaces / PumpShell 都是 [0,.05,-.035]；R03 FaceHardware 跟 Faceplate；R03 RearHardware 跟 RearCover；R05 UpperHardware 跟 UpperInterface。
  - R01_Fasteners 的向量是 [0,0,0]，分解时不动。
- **0–0.12 s 错峰按位移轴分三档，不是按组序号**（Stage:125）
  ```csharp
  float order = Mathf.Abs(exportedOffset.z) > .001f ? 0 : Mathf.Abs(exportedOffset.x) > .001f ? .06f : .12f;
  ```
  - `exportedOffset.z` 就是 Blender 的 Y（前后方向，窗口件和壳体）→ 0 s。
  - Blender X（侧向，管路、编码器）→ 0.06 s。
  - 只有 Blender Z（轴向）→ 0.12 s。
  - 合拢时倒序：`moveDelay = exploded ? motionOrder : .12f - motionOrder`（SMotion:96）。
- **0.46 s 缓动**（SMotion:100）
  - `Ease((moveAge - moveDelay)/.46f)`，Ease 是五次 smootherstep 6t⁵−15t⁴+10t³，有钳制，不回弹（SMotion:19-23）。
  - 改变目标时从当前机械位置重新起步（SMotion:93-96）。
  - 减少动态效果时直接到位；R05 演示期间跟随 DemoTime。
- **其他**
  - 分解模式下镜头距离 ×1.38（Stage:275），并自动取消折叠（Stage:153）。
  - 栅格舵折叠：绕 R04_FoldPivot 转 65°，用时 0.56 s（SMotion:111, 121, 123）。

## 1. 从 3D 场景自动生成图

**采集**（`MapGraphSceneCollector.Capture`，只能在 Edit Mode 运行，:23）
- **区域**：每个 `TargetZoneAuthoring` 是一个区域。矩形取它的 RangePoints 在 XZ 平面的包围盒，没有点时取中心 ±2 m（:28, :36-41, :224-231）。
- **未分区**：没有所属区域的群进入合成区域"未分区"（:58-64, :120）。
- **节点**：每个 `GameplayTargetClusterAuthoringBase` 是一个节点，类型为资源 / 敌人来源 / 撤离 / 独立活跃敌人（:29, :74-111）。被敌人来源群持有的活跃敌人群不单独成点（:43-54）。
- **稳定 ID**：区域和群为 `zone_` / `cluster_` 加 `Hash128(GlobalObjectId)`（:146-147）；边为 `edge_` 加 Hash128(有序端点对)（`MapGraphSceneNavigationScan.cs:149-153`）。
- **锚点候选**来自真实成员：资源接近点；出生点及其贴地投影和出生导航点；撤离成员位置；活跃敌人位置。候选按离群中心的距离排序（:72-115）。
- 同时采集 Agent 的导航配置（profile）与出生原点（:158-193），并生成场景、导航、运行时三个指纹（:123-143）。

**导航扫描**（`MapGraphSceneNavigationScan.cs:70-144`）
- 对每个群依次采样候选锚点，并检查从初始 Agent 原点出发是否 PathComplete，优先采用可达的候选（:89-123）。
- 然后对全部 N(N-1)/2 个群对做双向实测（:125-139）。正式图 27 群，即 351 对、702 次有向查询（`FormalSceneFacts.cs:12-13`；断言在 `MapGraphSceneCollectionTests.cs:103-104`）。

**候选边**
- 只有在所有 profile 下都双向可达、且未被人工禁连的群对才成为候选（`MapGraphConnectionCandidates.cs:60-66`）。
- 候选长度取各 profile 的（正向 + 反向）/2 中的最大值（:72）。

**两种生成方式**（模式枚举见 `MapGraphGenerationResult.cs:7`，分派见 `MapGraphGenerationController.cs:116-123`）

1. **`ConnectionsAndLayout`**：编辑器"从场景创建地图"（`MapGraphEditorWindow.cs:299-300`）。
   - **参考布局**：节点位置为世界 XZ × WorldToMapScale（当前为 1）。区域矩形为世界范围 × scale，四周各加 padding 40，最小 240×180（`MapGraphLayoutGenerator.cs:31-34, :53-58`）。
   - **选边**：4 种策略 Navigation / AxisWeak / AxisStrong / Geographic。做法类似 Kruskal：人工边先放入，每个节点度数不超过 4，得到生成森林（`MapGraphConnectionSeedBuilder.cs:11-12, :21-33, :49-58`）。
   - **定方向**：正交求解器回溯地给每条边分配左 / 右 / 上 / 下，每个节点 4 个端口互斥（`MapGraphOrthogonalLayoutSolver.cs:67-68, :129-139`）。
   - **解坐标**：横边合并 Y 对齐组，竖边合并 X 对齐组。然后迭代处理（`MapGraphLayoutCoordinates.cs:77-78, :100-103, :171-194, :108-126`；`MapGraphZoneLayout.cs:12-47`）：
     - 边两端最小间距 = max(网格间距, 两端半径和 + 留白 + 8)；
     - 节点之间分离（+12）；
     - 锁定区域夹紧；
     - 区域拟合与互相分离。
   - **打分**：可行解按 `MapGraphLayoutScore.cs:73-76` 评分取最小。扣分项有位移、方位反转、斜向关系被压平、距离失真、区域面积变化、线交叉。
   - **补边**：可选补边要求实测绕行比 ≥ 1.5，最多 ceil(边数 × 0.2) 条（`MapGraphShortcutGenerator.cs:30, :60`）。
2. **当前实际采用的是"网格摆放优先"流程**：`1 网格摆放` → `2 生成连接`(PlacementConnections) → `微调建议` → `校验线路` → `3 发布地图`（`MapGraphEditorWindow.cs:302-306, :317-318`；PL-GA `task_plan.md:7-15`）。
   - **摆放**：拖动吸附到网格（`MapGraphGridPlacement.cs:18-29`）；行 / 列按"坐标相等"重建（:41-66）。摆放不查导航，也不移动世界物体。
   - **生成连接**：冻结所有位置，按导航长度升序只接受已经同行或同列的候选（`MapGraphPlacementConnectionPlanner.cs:132-138`）。先保证连通，再最多加 ceil(N × 0.2) 条额外边，每加一条都整图做几何校验（:139-145）。人工边先保留（:122）。
   - **无解与微调**：固定位置无解时报 `PlacementConnectionsIncomplete`（:61-66）。微调在 ±1~4 格内移动未锁定的群，预算 min(512, 搜索上限)（:36-38, :70-116）。

## 2. 烘焙边长（`MapGraphNavigationCostService`）

**测量方式**
- `MeasureEdge` 做正、反两次 `AgentNavigationSegmentQuery.Calculate`（:151-158）。
- 每次先用 profile 的 SampleRadius 和高度容差对两端做 `NavMesh.SamplePosition`，高度差超出容差即失败；再调用 `NavMesh.CalculatePath(start,end,filter)`（`AgentNavigationSegmentQuery.cs:33-48, :66-76`）。
- 只有 PathComplete 才算数，长度为路径拐点折线长度之和（:78-97）。Partial 记为不可用，而不是长度 0（`MapGraphNavigationBakeData.cs:78-109`）。
- 只有正反两个方向都可用，这条边才有成本（:188-195）。

**使用哪个 profile**
- 来自场景中 `AgentPawnRoot` 上 `NavMeshAgent` 的序列化字段：agentTypeID、walkableMask、SampleRadius = max(0.5, 半径×2)、高度容差 = max(0.5, 高度×0.5)，以及项目的 32 个区域成本（`MapGraphSceneCollector.cs:158-193`）。运行时的等价物是 `AgentNavigationProfile.FromAgent`（`AgentNavigationProfile.cs:40-47`）。

- 当前值：agentTypeId 0、areaMask −1、sampleRadius 1、heightTolerance 1，区域 2 的成本为 2，其余为 1（SO :947-985）。

**何时烘焙**
- Editor 生成或校验时做全对实测。"应用预览"或"发布"时，由 `MapGraphNavigationBakeBuilder.Build` 选出最终图的边、核对锚点后写入（`MapGraphNavigationBakeBuilder.cs:17-47`；`MapGraphEditorDocument.cs:171-176`；`MapGraphAuthoringTransaction.cs:43, :79-80`）。

- 当前资产：26 条 bake 全部双向可用，正向长度 19.0–255.6 m、合计约 2539.5 m；bake `_revision: 14`，运行时指纹 `bf5f5c43…`（SO :942-946）。

**运行时判定 bake 是否仍可用**
- 条件是"指纹上下文匹配"且"profile 完全相等"（:51-56, :175-181）。
- 运行时安装器把场景指纹和导航指纹传为空字符串，因此只能走运行时指纹这一路（`MapGraphRouteEnvironmentService.cs:128`）。

**`LastInvalidationReason` 的取值**

| 取值 | 含义 | 位置 |
| --- | --- | --- |
| `BakeContextMismatch` | 指纹或 profile 不匹配（或 bake 里有重复 ID），全部边入队 | :56-62, :73 |

**运行时指纹**（`MapGraphNavigationFingerprint.cs:16-71`）
- 内容是 SHA256("MapNavigation:v2" + 对 `NavMesh.CalculateTriangulation()` 的规范几何签名 + 排序后的 Link / OffMeshLink / Surface 组件签名)。
- 几何签名精确保留顶点、共享关系、区域、绕序和重复几何，只规范枚举顺序（`MapGraphNavigationGeometrySignature.cs:9, :49-98`）。
- 场景里只要有活动的导航链接，指纹就带 `live-links:` 前缀，成本服务一律不信任 bake、全部补验（:68-70；CostService :53-55）。

**补验预算**
- 每帧 `Environments.Tick(2,4)`：最多 2 条边（即 4 次 CalculatePath）和 4 次锚点观察（Installer :159；EnvService :74-95）。
- 有待补边时 IsReady=false，新规划等待（EnvService :134；`AgentRouteController.cs:138`）；已有路线只要剩余边仍有成本就继续（:232-253）。

## 3. 导航孤岛

**检测只在 Editor 侧、基于实测矩阵完成；运行时没有专门的"孤岛"概念。**
- **扫描**：候选锚点采样成功后，还要验证从初始 Agent 可达。全部候选都不可达时，保留第一个合法采样，并标 `ReachableFromAgentOrigin=false`（`MapGraphSceneNavigationScan.cs:89-112`；PL-MC `p2_execution.md:290`；测试 `MapGraphSceneCollectionTests.cs:145-175`）。
- **分量**（`MapGraphNavigationValidation.cs:42-61`）：
  - 用双向都可用的群对建立物理分量。分量数 > 1 时报 `NavigationDisconnected`，只是警告（error:false）。
  - 禁连额外切开分量时报 `ExclusionsSplitNavigation`，也是警告。
  - 作者图把同一个可达分量拆开时报 `LostReachableConnectivity`，这是错误。
  - 分类设计见 PL-MC `p2_execution.md:172`。
- **结果**：孤岛群不会得到候选边，于是保留节点、不接任何边（`MapGraphConnectionGeneratorTests.cs:122-130`；`MapGraphPlacementConnectionsTests.cs:50-59`）。底层断言：两块分离的 NavMesh 之间返回 `PathPartial`、长度 +∞（`MapGraphNavigationTests.cs:88-104`）。

**`MapCommandNavigationIslandTests` 是真实场景的诊断/回归用例，不是检测器**（[T] `MapCommandNavigationIslandTests.cs:40-102`）
- 断言 bake 运行时指纹等于当前场景（:49），且成本缓存零补算（:50-53）。
- 记录 4 条"初始 Agent → 撤离点"路径，以及 4 个最近邻群到龙骨礁撤离群（`cluster_a84fd1c0…`）的路径；同时采集附近三角形、碰撞体和渲染器、向下射线，并截图（:57-99）。
- **只断言前 4 条（Agent → 撤离点）为 PathComplete**（:100-101）。邻群 → 龙骨礁的 4 条只是证据；"8 条全部 Complete"是运行日志里的观察（PL-MC `p6_execution.md:52`）。
- **历史根因**：龙骨礁撤离标记是悬浮的圆柱，NavMeshSurface 用 RenderMeshes 烘焙，把圆柱顶烘成了孤立的面（圆柱顶 10.36、烘焙面 10.50、邻近地面 6.83，`p6_execution.md:48`）。修复方法是让圆柱贴地并重新烘焙，没有给 Gameplay 加特殊寻路或伪造边（:50-52；验收报告 :37；PL-MC `architecture_review.md:279`）。
- 当前 SO 中该节点已有边（:549）和 bake（:1176）。

**路由中的处理**
- 没有成本的边对 Dijkstra 来说不存在（`MapGraphPathfindingService.cs:63-64`）。只有单向可达的边也不发布成本（CostService :191-194）。
- **玩家下令**（`AgentRoutePlanner.cs:80-88`）：
  - 从当前位置到所有候选入口都不可达时，规划失败为 `NoReachableEntry`；
  - 入口确定后在图上到不了目标时，失败为 `Disconnected`；
  - 提示文本"无法进入地图通路"、"没有可通行的群路线"（`AgentCommandFeedbackText.cs:143-144`）。
- **自主选择**：
  - 候选收集要先过 `CanSelectAutonomousRouteTarget`（`AgentTargetCandidateCollector.cs:115-116`）；
  - 图上不连通的候选在评分时被跳过（`AgentTargetDecisionController.cs:219-225`）；
  - 失败记忆对 Disconnected / NoReachableEntry / Unreachable / NavigationNotReady 无限期屏蔽，直到成本或目标修订、图、profile 变化，或 Agent 移动超过 2 m（`AgentRouteFailureMemory.cs:25-28, :48-52`）。
- **地图上不会把孤岛标灰**：节点"可用"只看 `CanTraverse`（目标存在且锚点有效），与导航是否连通无关（`MapGraphPresenter.cs:67-68`；`IAgentRouteTargetResolver.cs:45-46`）。

## 4. 路线执行与"同根重规划"

**提交与规划**
- `Submit`（`AgentRouteController.cs:69-96`）：自主请求在已有活动路线、待规划请求或反击期间被拒（Superseded）。新请求规划期间旧路线继续执行；新计划的首步被接受后才原子替换（:165-176）。
- 规划：每次 Tick 最多 4 次 NavMesh 查询，从当前地面位置到各候选入口锚点，取路径最短的作为入口（:150；Planner :55-82）。
- 然后固定入口，在作者图上 Dijkstra（`MapGraphPathfindingService.cs:30-82`）。注释原文："先固定入口，再按作者图寻路。不能换一个靠近终点的入口来绕过断边/途中群。"（Planner :85）

**逐群执行**（`AgentClusterStepExecutor`）
- 每群先 MoveTo 锚点，做到达检查（:73-88）。
- 已完成的群、中间的撤离群、容量撤离时的资源群只通行，但必须实际到过锚点（:90-96）。
- 其余的群：敌群逐个 Engage 直到清群，资源群 Search 并等待背包，最终撤离点 Extract（:115-125）。

**子步骤上限**（:32-33, :82, :102, :111-117）
- 到达失败或处理失败最多 3 次，间隔 0.5 s。
- 出生等待最多 5 s。
- 等待背包不限时。

**哪些失败触发重规划**
- 子步骤以 `StaleContext` / `Unreachable` / `NavigationNotReady` / `NoProgress` 失败时重规划；下一条边没有成本时以 `Disconnected` 重规划；其他失败直接结束整条路线（:120-126, :183-185）。

**同根重规划的确切流程**（:129-177, :193-213）
1. 复用 `_state.Request`，即同一个 RequestId、目标和来源；版本 `++_version`，标记 IsReplan；取消当前子步骤；发布 Planning(isReplan)。
2. 物理起点 `work.Origin = GroundPosition()`，就是当前位置（:143）。
3. 入图候选只取 `CaptureEntryNodes()`：当前游标所在节点；如果正在行进，再加上这条边的上一个节点（:204-213）。重规划不再放开全图入口（:144）。
4. 接受时 `ReplanCount` 继承，`EntryFromNodeId` 记录真实入边（:170-172, :214-220）。

**为什么叫"同根"、为什么限制入口**（文档依据）
- 不能把当前位置临时连到全图任意节点，否则会绕过作者连线（PL-MC `task_plan.md:175`）。
- 重规划保留原边两端作为入口候选（`p3_execution.md:40`）。
- `IsReplan` 标记是为了不把内部修复当成一条新的玩家指令（`p3_execution.md:28`；`AgentCommandFeedbackPresenter.cs:86`）。
- 子指令 ID 含根 ID 和版本，旧回调无法完成新版本（StepExecutor :177）。
- 同一路线重规划保留本轮搜索进度（HEAD `README.md:163`）。

**"有界"的含义**
- 每条根路线最多重规划 2 次：`if (_state == null || ++_state.ReplanCount > 2) EndActive(Failed)`（:198-199），计数跨次继承（:172）。
- 每次规划墙钟期限 8 s，超时以 NavigationNotReady 失败（:130, :136-137）。
- 规划结果过期（环境变化，或规划期间移动超过 2 m）可重启，最多 3 次，之后以 StaleContext 失败（:153-161）。
- 重规划的规划失败直接结束整条根路线（:255-260），不会回退成直接走向终点（`p3_execution.md:27`）。
- 安装器在重规划时使当前边失效并补测（2 次查询）（Installer :217-226）。这与报告中"edgeQueries 在 4→5 期间 0→2"一致（验收报告 :58）。
- 反击期间不重规划（:140, :195）。反击恢复走 Lifecycle 挂起再恢复原子指令，是另一套机制（`group_aggro_manual_resume_report.md:12`）。

**报告中的实例**
- MR04：事件 737 旧子指令 `MoveTo:NoProgress` → 739/741 同根 `Route_ff6d0b2e…` 从版本 4 到 5 → 774 Completed。接受间隔 0.0272 s，完成耗时 3.0820 s，平面位移 6.9493 m（验收报告 :54；`p6_execution.md:142, :160`）。
- 设计依据原文："原根控制器明确允许最多两次重规划，每次规划期限 8 秒"（`p6_execution.md:142`）。
- 离线判定"已恢复"的条件：唯一一次 NoProgress，同根、同终点、同来源，下一版本依次出现 Planning→Accepted→Completed，且有真实位移。其余情况一律算未恢复（PL-MC `architecture_review.md:315`；`p6_execution.md:151`）。
