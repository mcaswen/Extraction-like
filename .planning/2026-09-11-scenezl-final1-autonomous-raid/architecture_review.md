## 2. 文件归属和依赖审查

| 审查项 | 结论 |
| --- | --- |
| Editor/Runtime 分离 | Editor 负责场景资产/Play Mode/构建；Automation Runtime 不引用 UnityEditor 或 NUnit，可供验证 Player 使用 |
| Gameplay 依赖方向 | Automation 单向依赖 Gameplay；业务事件不引用测试、文件系统、报告或进程层 |
| 目标决定权 | Driver 只处理正式节点报告的实际资源；不包含 Collector、CommandRouter 或自动撤离脚本 |
| 资源状态所有权 | 搜索/全局完成归正式资源业务，背包会话归 Backpack；测试不能写 IsSearched、Looted、Blackboard 或仓库结果 |
| 扫描/缓存/移动 | 增量候选状态和短期可达事实归 Targeting；执行路径归 NavigationMotor；资源几何归 ResourceCluster；Zone 轮廓归 Targets |
| 单例/结算 | 场景明确一个 RaidFlow 所有者，presence 按 Agent，计时/结算保持 Raid 所有权；不加另一个完成判定器控制游戏 |
| 文件清单 | Reuse/Extend/Wrap/Create 已列具体文件路径和新文件独立理由；条件新增的扫描/缓存文件需按采样决定，不机械全建 |
| 普通构建边界 | 自动化只在 Editor 或显式自动化宏构建中存在，正常 Player 不安装背包机器人 |

## 3. 性能方案审查

- 优先级符合用户实测：Discovery → Pawn → Zone，再由证据决定 FFT、墙体、小地图、地形和 URP。
- 没有只降低 Update 频率的笼统方案。查询数量、完整扫描年龄、路径失效、即时伤害/开火检查、静态/动态轮廓分别设置约束。
- 1 ms 调度时间预算不能打断一次同步 NavMesh 查询，这个限制已明确；必要时单独解决导航复杂度。
- 最终性能包含真实渲染，Editor 和 Player 分开。无图形、离屏截图循环、暂停 UI 或提前阵亡不能替代完整游戏测量。
- 平均 FPS、P99、1% Low、持续低帧和最大卡顿均有定义。用户已确认 4K 高画质及主规划组合门槛，未宣称实测达标。
- 日志有频率/容量/丢失检查，采样有效性和自身成本需要测试；不把 unavailable 的 GPU 数值记为零，不删除不利帧。

- 原场景自然回合与构造变体分开，前者禁止测试下指令/传送/补伤害/清空资源，后者必须记录准备差异。
- 成功要求行为、覆盖、帧率、持久化和进程证据同时满足，不只观察角色消失或成功 UI。
- 对两个 Agent 的要求来自原场景配置，不能只相信一个可能漏捕获角色的运行时要求集合；应核对预期 `{1,2}`、实际注册集合、要求撤离集合和最终结算集合。
- 背包的物品数量核对应使用正式物品 ID、数量和容器关系；运行时物品实例 ID 可能随 UI 重建变化，不能把这种变化误判为丢失。真实增减、堆叠、价值和持久化分别核对。

- 正常 Domain Reload 和同进程第二局明确覆盖，不依赖旧夹具关闭重载的配置掩盖静态状态问题。
